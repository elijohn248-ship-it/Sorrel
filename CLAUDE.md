# Sorrel

Sorrel (formerly Drift) is the owner's daily macOS browser: Arc-style Spaces and sidebar, Safari's engine (WebKit), Helium-style privacy, bangs, and Safari-style extensions with uBlock Origin Lite built in. It is a single-person project; there are no other users yet.

## Name, and the rename from Drift

The app was called **Drift** until 2026-11-14; it is now **Sorrel** ("Sorrel Browser"). The name was chosen after conflict checks: Flow, Breeze, Cove, Wren, Lagoon, Tern, Fern and Moss are already used by other browsers (many are new Arc replacements from Oct–Nov 2026, as Arc shuts down on 2026-12-22). `sorrelbrowser.com`, `sorrel-browser.com` and the GitHub names `sorrelbrowser`/`sorrel-browser` were free then; the US trademark search is still the owner's to do. The icon (redrawn 2026-11-14) is one solid deep-green sorrel leaf with a single cut-through midrib, leaning right on a quiet lavender -> sky -> mint tile; `tools/make-icon.swift` holds the design constants and also writes `Resources/logo.svg`, the vector master of the same mark.

Everything is renamed: bundle id `app.sorrel.browser`, `Sources/Sorrel`, the `Sorrel` SwiftPM target, `SORREL_*` test variables, `sorrel://` for bundled pages, the profile folder `~/Library/Application Support/Sorrel`, and the project folder `~/sorrel` (`~/drift` is a symlink to it so old references still resolve). The only deliberate "drift" left in code is a `drift://` -> `sorrel://` fallback in `Engine.load`.

**The Drift -> Sorrel copy** ran on the owner's first Sorrel launch (2026-11-14). Its code was replaced by the sandbox move below (it is in git history before the `sandbox` branch). **The Drift originals (`Application Support/Drift`, `WebKit/app.drift.browser`, `HTTPStorages/app.drift.browser*`) are the owner's backup: delete them only when the owner says so.**

## Sandbox

Sorrel runs in the macOS **App Sandbox** (`Resources/Sorrel.entitlements`, ad-hoc signed, hardened runtime). The point: a page or extension that compromised Sorrel's main process still couldn't read the owner's files, SSH keys, other apps' data, or run things freely. Inside it, Foundation's home folder (`NSHomeDirectory`, `homeDirectoryForCurrentUser`, `~/Library` lookups) is the container `~/Library/Containers/app.sorrel.browser/Data`; use `Sandbox.realHome` / `Sandbox.downloads` (Support.swift) when you mean the person's real folders. `Sandbox.isOn` tells you if it's active.

- **Entitlements, keep the list short:** network client; camera + microphone; `~/Downloads` read-write; files the person picks in an Open panel (read-only: uploads, adding an extension); printing; and read-only temporary exceptions for `~/Applications` (Safari extensions, fallback browser) and the pre-sandbox data the move copies. Add an entitlement only when a feature is refused under the sandbox, and say why in the file.
- **Child processes inherit the sandbox but not access to picked files**: `ditto` unpacks a private copy of a picked zip (Extensions.add). `screencapture` from inside the app no longer works.
- **Ad-hoc signing is fine**: a rebuilt app (new code hash) keeps opening its container without prompts (tested 2026-11-14). No certificate needed.
- **Layout inside the container differs from outside** (found by experiment): WebKit keeps `Library/WebKit/WebsiteData`, `WebExtensions`, `ContentRuleLists` *without* the bundle-id folder, and the cookie jar is `Library/Cookies/Cookies.binarycookies`, not `HTTPStorages/<id>.binarycookies`.
- **The move (`Migration.swift`, first thing in `main.swift`).** On the first sandboxed launch (no `SORREL_HOME`; container has no `Application Support/Sorrel`; the real one exists) Sorrel COPIES, never moves: each item of `~/Library/WebKit/app.sorrel.browser/` -> `WebKit/<item>`, `HTTPStorages/app.sorrel.browser.binarycookies` -> `Cookies/Cookies.binarycookies`, `HTTPStorages/app.sorrel.browser/`, then `Application Support/Sorrel` (last; it marks the move done), via `.migrating` temp names; anything already in the way is set aside as `*.before-migration-<time>`. Then it merges the old preferences plist and writes `moved-into-sandbox.txt`. It refuses while an older Sorrel is running (offers to quit it), and on failure quits without keeping a partial copy, so the next launch retries. **The originals in `~/Library` stay as the owner's backup** and are what an unsandboxed build would still open. Verified end to end with the test build (cookie + open tab carried over). **The owner's real move ran on 2026-11-15** (`moved-into-sandbox.txt` in the container's profile), so the container is now the live profile. `SORREL_MIGRATE_TEST=<from Library>:<to Library>` runs just the copy between stand-in folders.
- **Window snapshots can't see page content under the sandbox**: `SORREL_SNAPSHOT` (cacheDisplay) shows the web area blank; the page is fine. Use `SORREL_WEBSNAPSHOT=<png>` for WebKit's own picture of the selected page.

## Non-negotiables

- **WebKit (WKWebView), never Chromium.** The owner values battery life and low upkeep. Don't propose Chromium, CEF or Electron.
- **Free to run.** No paid Apple developer account (the app is ad-hoc signed), no paid services. Phone sync, when it comes, is a PWA on Cloudflare's free tier.
- **As private as Helium.** No telemetry. Ads and trackers blocked. Only two deliberate exceptions to "sites see Safari": the sites a Chrome-store extension lists under `externally_connectable` (e.g. Proton's sign-in pages) see a Chrome user agent and get a `chrome.runtime` bridge, because that's how they hand off to the extension.
- **Never touch the real profile from tests.** The real profile is in Sorrel's container (`~/Library/Containers/app.sorrel.browser`), with the pre-sandbox copy in `~/Library/Application Support/Sorrel`. Every test run uses **`build/SorrelTest.app`** (bundle id `app.sorrel.browser.test`: its own container, preferences and site data) and sets `SORREL_HOME` to a scratch folder under `/private/tmp` (see Testing). `Sorrel.app` refuses to start with `SORREL_HOME` set, and drops every other `SORREL_*` variable at launch (main.swift): test hooks work only in `SorrelTest.app`. With it set, cookies and site data also stay in memory (`Engine.store(for:)` returns one non-persistent store): WebKit files persistent site data by bundle id, not by profile folder, so before 2026-11-14 test runs were writing into the owner's real cookie jar. Keep it that way. Launching the app without `SORREL_HOME` is the owner's job, never an agent's.
- **Test windows must stay in the background.** The owner uses the Mac while work happens. Test runs (any run with `SORREL_SNAPSHOT` set) open behind other windows, take no focus and show no Dock icon. Keep that behaviour; `SORREL_LOUD=1` is the only override. Warn before anything that will take focus.
- **Don't loop on state only the owner can see.** Signed-in extension behaviour, hover feel, drag and drop: after one or two rounds, stop and give the owner a specific thing to try and what to paste back.

## Working in parallel (several agents at once)

The owner runs several Claude sessions at the same time. **Sessions must not share a working folder**: one session's half-finished edit breaks every other session's build (it happened twice on 2026-11-14).

- `~/sorrel` is `main` and the copy the owner runs (`build/Sorrel.app`). While other sessions are active, don't do feature work directly in it.
- Each task gets its own git worktree and branch: `cd ~/sorrel && git worktree add ../sorrel-<task> -b <task>` (or Claude Code's worktree option). Edit, build and test only there; each worktree has its own `.build/` and `build/`, and its first build takes a few minutes.
- Start every session with `git worktree list` and `git status` to see what's in flight.
- Before reporting a task done: commit on its branch, merge `main` into it, rebuild, and rerun the tests that cover what changed. Resolve conflicts in the worktree, never in `~/sorrel`.
- **The owner decides what merges.** Agents don't merge into `main` or push unless asked. `origin` (`github.com/elijohn248-ship-it/sorrel`) is **public**: anything pushed, this file included, is visible to everyone, so never commit keys, tokens or the owner's personal data (secrets live in `~/.config/sorrel`, outside the repo).
- Merged so far (2026-11-14/15): `sandbox`, `fluid-animations`, extensions work, `updater`. The `sandbox` worktree (`~/sorrel-sandbox`) is merged and can be removed when the owner says. When asked: `cd ~/sorrel && git merge <task> && ./build.sh`, then `git worktree remove ../sorrel-<task> && git branch -d <task>`, and tell the owner to quit and reopen Sorrel.
- Collision hotspots, so keep diffs there small and local: `App.swift` (every test hook; add a new hook as its own `if env[...]` block, don't reshuffle others), `Web.swift`, `SettingsWindow.swift`, `Support.swift` (each new setting needs a field AND a decoder line), and this file (edit only the section you're changing).
- Tests from different worktrees can run at the same time: each uses its own scratch `SORREL_HOME` and in-memory site data. Each test launch still opens a background window, so keep runs batched.

## Build and run

Only Command Line Tools are installed (no Xcode), so this is a SwiftPM build that `build.sh` wraps into an app bundle.

```
./build.sh            # release build -> build/Sorrel.app
./build.sh run        # build and open
./build.sh install    # build and copy to /Applications
open build/Sorrel.app  # open the current build
```

Minimum macOS is 15.4 (needed for `WKWebExtension`). The owner runs the build from `build/`; after a rebuild they must quit and reopen Sorrel to get it. Say so every time.

`Info.plist` sets `MallocSpaceEfficient=1` (see Memory). `main.swift` re-execs once with it if a launch lacks it.

Signing is ad-hoc **with the hardened runtime and the App Sandbox** (`build.sh`: `--options runtime --entitlements Resources/Sorrel.entitlements`; see Sandbox). Each app also carries `Contents/XPCServices/SorrelUpdater.xpc` (the `SorrelUpdater` target, signed *without* the sandbox; see Updates). Every build makes two apps from one compile: `build/Sorrel.app` (the owner's) and `build/SorrelTest.app` (tests only; `build.sh` derives its Info.plist and entitlements from the real ones: bundle id `+.test`, display name Sorrel Test, no http/https handler, plus read-write on `/private/tmp/`). ATS uses `NSAllowsArbitraryLoadsInWebContent`: web pages may still load http://, but Sorrel's own requests (lists, updates, favicons, suggestions) must be HTTPS.

## How the pieces behave

- **Motion (`Motion`, Support.swift):** every slide, fade and pop uses the same three curves: `settle` (arriving), `leave` (going), `glide` (a state change). `Motion.run` wraps `NSAnimationContext`, `Motion.layer` wraps a `CATransaction`, `CALayer.popIn/popOut/press` move only the picture (never the model values), and `NSView.fade(in:)` replaces flipping `isHidden`. Reduce Motion drops movement and keeps fades. Sidebar rows and favorites keep their highlight in a layer so hover/selection crossfade; the outline slides single rows in and out (`reloadOutline` diffs the top level and falls back to `reloadData` for moves or folder changes). Add new animations through these helpers rather than ad-hoc durations.
- **Sidebar hover:** `MainWindowController` modes `pinned` / `hidden` / `peeking`. Reveal strip width, overshoot reach, hide delay and slide speed are all in `settings.json` and Settings ▸ Sidebar. While peeking, a 40 ms timer watches the real cursor (events stop arriving once it leaves the window; plain timers pause during menus/drags, which is wanted).
- **Command bar:** ⌘T = centered bar. ⌘L and clicking the address box = in-place editor anchored on the pill. A `focusHolder` on `SorrelWindow` stops pages stealing focus while the bar is open.
- **Peek (link preview):** any clicked link to a different site opens over the page; ⌘O expands, Esc closes. Excluded on search engines (`peekExcludedSites`) and off for script-opened windows (sign-in pop-ups must still work).
- **Split view:** a split is an `Item` with `split: SplitLayout` (stacked flag + pane fractions) and 2–4 tabs in `children`, so it moves, pins, archives and saves as one unit, shown as one sidebar row. `Space.selectedID` is the *focused pane*, so the address box, ⌘L, ⌘W, find and extensions all act on it. Clicking into a pane focuses it (local mouse-down monitor). Closing a pane of an unpinned split closes that tab; in a pinned split it sleeps. One tab left = the split dissolves. Favorites can't be in a split. Store API: `makeSplit`, `removeFromSplit`, `unsplit`, `split(containing:)`, `unit(_:)`. Ways in: ⌃⇧= (command bar opens a pick beside the current tab), right-click a tab ▸ Open in Split View, drag a tab onto the page's left/right/top/bottom, drop a tab on a split row, or the split button on Peek. ⌃⇧- separates, ⌃⇧] / ⌃⇧[ move focus.
- **Row button (`TabActionButton`, Sidebar.swift):** pinned tabs and pinned split rows show "−" on hover while loaded (unload = `Store.close`, which sleeps them), then the two strokes rotate into "×", which runs `Store.closeAndUnpin` (out of the sidebar; ⌘⇧T reopens each tab unpinned). Clicks within 0.35 s of the change are ignored so a double-click can't remove the tab. Unpinned tabs show "×" as before. The strokes sit in one group layer so their transparency isn't doubled where they overlap.
- **Spaces:** each can keep separate logins (`profileID` -> `WKWebsiteDataStore(forIdentifier:)`). Favorites are shared across spaces.
- **Archiving / sleeping:** unpinned tabs idle > `archiveAfterHours` are archived (Tabs ▸ Archived Tabs). Any tab idle > `sleepTabsAfterMinutes` is unloaded; `interactionState` is saved so it wakes with history and scroll.
- **Blocking:** built-in lists (`Blocker.swift`) always cover private windows and the first 25 s after launch; once uBlock Origin Lite's rules are active it takes over on normal pages (`blockerInCharge`). **Never call `removeAllContentRuleLists()`**: it wipes the extension's rules too. Remove only our own lists.
- **Extensions:** `Extensions.shared` hosts them; `ExtensionTab`/`ExtensionWindow` adapt Sorrel's model. Bundled uBOL is unpacked to `BundledExtensions/` because **WebKit crashes (SIGKILL) if an extension's files sit inside the app bundle.** Safari extensions found in `/Applications/*/Contents/PlugIns/*.appex` are listed off-by-default. Chrome Web Store installs download the `.crx`, strip its header, and keep the real 32-letter id as `uniqueIdentifier`/base URL (the extension's own site addresses it by that id).
- **Extension buttons are live.** The icons in the address box show each extension's `WKWebExtension.Action` for the *selected tab*: its current icon, badge (drawn as a small red count), label as tooltip, and dimmed when the extension disables it for that site. `didUpdate action` posts `.sorrelExtensionAction`; the sidebar also refreshes on `.sorrelSelection` because actions are per tab. Right-click an icon for the extension's own menu items plus its keyboard shortcuts (`WKWebExtension.Command.menuItem`, ready to perform).
- **Extension keyboard shortcuts** (manifest `commands`) work: the key monitor in `App.swift` tries Sorrel's own `Keybindings` first, then `Extensions.handleKey` (`context.command(for:)` / `performCommand(for:)`), so Sorrel's bindings always win a clash. WebKit maps Chrome's `Ctrl+Shift+X` to ⇧⌘X on the Mac. Settings ▸ Extensions lists each extension's shortcuts. Shortcuts are not user-remappable yet (WebKit allows it: `activationKey`/`modifierFlags` are settable; it would need storing).
- **Chrome Web Store extensions update themselves** (`updateChromeExtensionsIfNeeded`): every 3 days (stamp `Extensions/last-update-check`, gated by the same `autoUpdateBlocker` setting as uBOL), or from View ▸ Check for Extension Updates / the button in Settings ▸ Extensions. A newer `.crx` is unpacked to `Extensions/chrome-<id>.update` and swapped in by `applyPendingChromeUpdates` at the next launch (or at once if the extension is switched off), never under a running extension. Storage lives in WebKit's store under the extension's id, so sign-ins survive. `discover` ignores `*.update`, `*.old` and `*.partial` folders. Tests point `SORREL_CRX_DIR` at a folder of `<id>.crx` files instead of the store.
- **Background start retry:** WebKit now and then failed Proton Pass's very first background start right after launch (its script ran as if the compat shim were absent; the same profile passed moments later). `startBackground` gives one failed start a second go after 2 s before reporting it. Seen only in test profiles on their first run; not reproducible on demand.
- **ChromeCompat:** adds inert stand-ins for Chrome-only APIs (`runtime.onUpdateAvailable`, `offscreen`, `idle`, …), a `requestIdleCallback` polyfill (and a private copy inside page-world scripts that need it), and **pins `globalThis.chrome`/`browser`** because Proton Pass replaces them with a locked Proxy and WebKit then silently drops every message. It only ever *adds*; **never wrap or Proxy the extension API, and never reassign `sendMessage`/`addListener`, even for tracing: delivery stops.** Bump `ChromeCompat.version` when you change it so installed copies re-patch (13 since 2026-11-15: wildcard `externally_connectable` hosts dropped from the bridge). Version 12 also collapses the Drift-era chain (`sorrel-background.js` -> `drift-background.js` -> `drift-chrome-compat.js`) that copies patched before the rename still had: the loader now imports the extension's real worker directly and the `drift-*` files, manifest keys and HTML tags are removed.
- **Pop-up sizing:** WebKit sizes action pop-ups to content; Chrome pop-ups that declare a fixed size (Proton: 600×430) collapse to a strip. `applyDeclaredSize` reads the size from the extension's stylesheet (not the live page) and sets `min-width/min-height` so WebKit's popover grows. Hosting `popupWebView` in our own popover does not work (WebKit keeps resizing it).

- **Security behaviour (keep it):** HTTPS-first (`httpsFirst`, on by default): main-frame http:// GETs to ordinary hosts are retried as https://; if that fails or bounces back to http://, `showInsecureWarning` shows Sorrel's own page, and its Continue button (`sorrel-insecure:continue`, honoured only while that warning is up in that web view) allows the host until quit. Local names, IPs and non-80 ports are never upgraded. Sorrel's own error/warning pages go through `loadInternalPage` so navigation policy lets them through. Pages opening other apps (`openInOtherApp`) ask first, except clicked mailto/tel/sms/facetime links; grants last until quit. Main-frame `data:` navigations are blocked. Downloads are quarantined (WebKit does it; Sorrel drops the source addresses for private windows). ⌘/middle-click from a private window opens another private window, never a normal tab. Camera/mic choices are keyed by asker + top site, and never remembered in private windows. Favicon fetches are https only and carry the page's user agent. Extensions get only manifest-required permissions on switch-on; optional ones go through the prompt delegates and approvals persist in `settings.json` `extensionGrants`. What a manifest required at switch-on is recorded in `extensionApproved`; an update (Chrome Web Store or uBOL) that requires more is held back with the extension off until the person agrees (tests never ask: they log `ext: … held back`). Added 2026-11-15 (security audit): the address box drops only a *leading* `www.` (`Site.display`), cuts long hosts at the front so the real domain stays visible, and shows an orange open lock on http:// pages; JS dialogs and sign-in prompts from tabs that aren't on screen are answered "Cancel" at once (never an app-modal dialog), and from a page's second dialog on there is "Don't let this page show more dialogs" (until it navigates); the not-secure Continue works only while that warning is the page showing; downloads a page starts without a click (`WKDownload.isUserInitiated` false) ask once per site until quit (hidden tabs and tests: blocked, toast); `sorrel://` names must be `[a-z0-9-]+`; a page that crashes its web process more than twice a minute gets the error page instead of endless reloads.

## Updates

Sorrel updates itself from the owner's GitHub releases, free and without Apple: **`UpdateConfig.repository`** (`Sources/SorrelUpdateCore/UpdateCore.swift`, currently `elijohn248-ship-it/sorrel`, which is `origin`) and the feed `https://github.com/<repo>/releases/latest/download/updates.json`, which GitHub redirects to the newest published release's asset. Built 2026-11-15 and merged into `main`; `main` was first pushed to that repository on 2026-11-15. **No release has been published yet**: the app is still 0.1.0 (build 1), so the first `tools/release.sh` should be 0.2.0 or similar.

- **Releasing:** `tools/release.sh 0.2.0` bumps `CFBundleShortVersionString` to 0.2.0 and `CFBundleVersion` by one (the build number is the only thing compared, so it must only ever go up), builds, zips `build/Sorrel.app` (`ditto --keepParent`), signs the zip, writes `dist/` (zip, `updates.json`, `notes.md`, `release.env`), commits "Sorrel 0.2.0 (build N)" and tags `v0.2.0`. Nothing leaves the Mac until **`tools/release.sh publish`**: push, GitHub release with both assets (via `gh`, or `GITHUB_TOKEN` / `~/.config/sorrel/github-token` through the REST API; neither `gh` nor Homebrew is installed, and the token file exists, so the REST path is the one in use), then it polls the feed. Cutting is an agent's job when asked; **publishing is the owner's go-ahead** (it reaches every installed copy).
- **Signing key:** Ed25519 via CryptoKit, `tools/update-sign.swift`. The private key is `~/.config/sorrel/update-signing-key` (mode 600, never in git); its public half is `UpdateConfig.publicKey`. **If the private key is lost, no installed copy can ever accept another update** (they'd all need a fresh download): the owner should keep a copy in their password manager. `release.sh` refuses to cut with a key that doesn't match the built-in public key.
- **In the app (`Updater.swift`):** 30 s after launch and every 30 min it checks whether 6 h have passed (`Updates/last-check`), gated by the `checkForUpdates` setting (Settings ▸ General ▸ Updates, with version, Check Now / Relaunch to Update, status); Sorrel ▸ Check for Updates… (`updates.check`) checks at once. A newer `build` is downloaded to `Updates/Sorrel-<build>.zip` (ephemeral session, no identifying request), checked against size, sha256 and the Ed25519 signature; a failed check deletes it and says so. A verified zip is "ready": toast + the menu item becomes "Relaunch to Update to X…", and **it installs when Sorrel quits** (`applicationShouldTerminate` returns `terminateLater` until the service has it) or at once from the menu / the Settings button. The next launch toasts "Sorrel updated to X" (`Updates/installing` marker). The feed and zip requests are the only network traffic; nothing about the person or Mac is sent.
- **Installing (`SorrelUpdater.xpc`, unsandboxed on purpose):** the sandboxed app can't write to /Applications, and children inherit the sandbox, so the swap is done by an XPC service launchd starts for the app (`Contents/XPCServices/SorrelUpdater.xpc`, bundle id = app id + `.updater`, built from `Sources/SorrelUpdater`, ad-hoc + hardened runtime, **no entitlements**). It treats everything the app sends as hostile (security audit, 2026-11-15): it installs only over **the bundle that contains it** (three levels up from the .xpc; the app no longer names a path), checks that bundle's id equals its own minus `.updater`, **reads the zip once, verifies those bytes in memory and keeps a private copy in `~/Library/Caches/<service id>/`** (out of the sandbox's reach, so the app can't swap the file after the check; the installer accepts only such a copy and deletes it afterwards), and **writes its log only to the app's own `Updates/update.log`** (inside `~/Library/Containers/<app id>/Data/`, or under `/private/tmp` for the test build; no symlinks or hard links, control characters stripped). Note: launchd starts the service with the app's environment, so Foundation's home folder there is the app's container; the service uses `getpwuid` for the real home. Then it `posix_spawn`s itself as a detached installer (`POSIX_SPAWN_SETSID`, because launchd ends the service with the app) which waits for the app's pid to exit, `ditto -x -k`s the zip beside the app (or inside the bundle, swapping `Contents`, if the folder isn't writable), refuses a bundle with another id or a build that isn't newer, runs `codesign --verify --deep --strict`, strips `com.apple.quarantine` from every file (otherwise Gatekeeper would refuse the ad-hoc app), swaps with two renames, and `open`s the app if asked. Everything is logged to `Updates/update.log`. Verified 2026-11-15 with `tools/update-test.sh` both under /private/tmp and in /Applications (no App Management prompt appeared for this admin account).
- **Known limits:** an app run straight from Downloads is translocated (`/AppTranslocation/`); Sorrel then explains to move it to Applications instead of trying. Ad-hoc signing means a new build has a new code hash: camera/microphone grants may be asked again after an update, as after any rebuild. First launch of a downloaded copy still needs System Settings ▸ Privacy & Security ▸ Open Anyway (no notarization); the release notes template says so. There is no key rotation: changing the key means every user downloads afresh. Downgrades are refused everywhere (a feed pointing at an older build does nothing).
- **Testing:** `SORREL_UPDATETEST=version|check|install|quit` with `SORREL_UPDATE_FEED=file:///…/updates.json` (honoured only by the test build): `version` logs what is running and quits, `check` finds/downloads/verifies and quits without installing, `install` is the Relaunch to Update path (relaunch off in tests, so no window takes focus), `quit` is install on quit. `badlog` (four log paths the service must refuse), `swapzip` (overwrites the zip right after the handoff and tries to reach the service's private copy; the checked bytes must still install; logs inside the test app's container like the real app) and `containerlog` (prints that container log) cover the audit fixes. `tools/update-test.sh [folder]` does the whole thing with throwaway copies of `SorrelTest.app` and three fake newer builds signed with the real key; pass `/Applications` to test the real location (it removes `SorrelTest.app` from there afterwards). Output lines start with `updater:`. Quiet test runs never check for updates unless `SORREL_UPDATETEST` is set.

## Memory

Measure with `footprint -p <pid>`, not resident size: WebKit leaves 1 GB+ of reclaimable pages that `ps` counts. With uBOL on, the main process was ~235 MB of true footprint from malloc fragmentation after rule loading; `MallocSpaceEfficient=1` brings it to ~45 MB. Things that did not help: `malloc_zone_pressure_relief`, `MallocAggressiveMadvise`, trimming uBOL's unused rule sets.

## Testing

There is no test target. Tests are the app itself, driven by environment variables read in `App.swift` (`runDebugHooks`). Pattern:

```
S=$(mktemp -d /private/tmp/sorrel-test.XXXXXX); mkdir $S/p1
SORREL_HOME=$S/p1 SORREL_SNAPSHOT=$S/shot.png SORREL_DELAY=8 SORREL_OPEN=https://example.com build/SorrelTest.app/Contents/MacOS/Sorrel 2>&1 | grep -E '^(selected|hover|peek|ext|ui|diag|autofill):?'
```

Scratch folders must be under `/private/tmp` (the only place outside its container the sandboxed test build may write). `SORREL_SNAPSHOT` = quiet test mode + where to write a PNG of the window (web content comes out blank under the sandbox: add `SORREL_WEBSNAPSHOT=<png>` for the page itself); the app quits itself after `SORREL_DELAY` seconds. Useful hooks: `SORREL_OPEN` (tab to open), `SORREL_RUN=cmd,cmd` (commands), `SORREL_SIDEBAR=hidden|peek`, `SORREL_COMMAND=<text>` (type into ⌘T bar), `SORREL_EDITADDR`, `SORREL_HOVERTEST`, `SORREL_PEEKTEST=expand|close|unpinned|samesite|othersite`, `SORREL_FEATURETEST` (shortcuts, archive, private), `SORREL_DAILYTEST` (sleep, downloads, suggestions, history, update check), `SORREL_BLOCKTEST`, `SORREL_EXTTEST=1|ui|protonpass`, `SORREL_EXTACTIONTEST=<id part>` (logs every loaded extension's action state and shortcuts, then presses the named extension's first shortcut), `SORREL_EXTUPDATETEST=1` with `SORREL_CRX_DIR=<dir of id.crx>` (Chrome-store update check against local files; a fake newer .crx is `Cr24` + version 3 + header length + header + zip), `SORREL_EXTDIAG=<id part>` (passive extension diagnostics: errors, a read-only message listener, heartbeat, pop-up layout dump), `SORREL_AUTOFILLTEST`, `SORREL_MIGRATE_TEST=<from>:<to>` (runs the sandbox move's copy between two stand-in Library folders and exits), `SORREL_COOKIETEST=set|check` (a lasting example.com cookie across launches; only meaningful without `SORREL_HOME`, i.e. in SorrelTest's own container profile), `SORREL_SECTEST2` (audit fixes: leftover Continue offer refused, hidden-tab dialogs answered at once, `sorrel://../` refused while `sorrel://welcome` loads, a page-started download blocked; set `SORREL_DOWNLOADS` to a scratch folder), `SORREL_SECTEST` (HTTPS upgrade + not-secure warning + Continue, private ⌘-click, data: block, other-app prompt, download quarantine; `SORREL_SECTEST_HTTP=<http url>` picks the no-https site, default expired.badssl.com), `SORREL_SPLITTEST=1|reopen` (split view end to end; `reopen` just logs what a relaunch restored), `SORREL_EMOJITEST=open|search:<q>,pick` (emoji sheet; pair with `SORREL_SNAPSHOT_CUSTOMIZE=<png>`), `SORREL_EXTERNALTEST`, `SORREL_EXT_STORE=<uuid>` (persistent extension store for a test, inside SorrelTest's container), `SORREL_DOWNLOADS=<dir>`, `SORREL_DOWNLOADTEST=1|reopen` (with `SORREL_DOWNLOADS`: a real download plus stand-ins for running/cancelled/picture, logs `dl:` rows and the button ring, writes `panel.png` and `window.png` into the downloads folder; `reopen` on the same `SORREL_HOME` checks what was remembered, then clears it), `SORREL_UPDATETEST=version|check|install|quit` + `SORREL_UPDATE_FEED` (Sorrel's own updater; see Updates and `tools/update-test.sh`).

To test an extension the owner has added, copy it from the real profile's `Extensions/` into the scratch profile; never run tests against the real profile. **Chrome Web Store downloads are not allowed from tests** (blocked as external communication); use the copy that is already installed. A tiny echo extension (manifest + one-line background that answers messages) is the fastest way to separate a WebKit limit from an extension quirk. In quiet test mode pages are `visibilityState: hidden`, so CSS fade-ins never run and pop-up screenshots can be blank even when the page rendered; check `innerText`, not pixels.

Known limits of what tests can show: real mouse feel, drag and drop, and anything behind the owner's sign-ins. Ask the owner for those.

## Polish phase: rules and workflow

Sorrel is basically built. The job now is fixing bugs and hardening it into a complete, private, secure browser. Prefer small, verified changes over rewrites.

### Hard rules
1. **Never weaken a security or privacy setting to fix a bug.** If a site breaks because of blocking, the sandbox, or a permission prompt, add a narrow per-site exception or ask me. Why: a privacy browser that leaks once isn't private.
2. **No new outbound network calls** beyond what exists (page loads, filter-list updates, the updater). No analytics, crash reporting, or telemetry, ever. Why: privacy is the product.
3. **No new entitlements or temporary exceptions.** Resources/Sorrel.entitlements should only shrink. Ask before touching it.
4. **No page-to-app JavaScript bridge.** There are no WKScriptMessageHandlers today; keep it that way unless I approve one. Scripts the app injects never paste page-controlled strings into JavaScript source; pass values as arguments (callAsyncJavaScript arguments:) instead.
5. **Every bug fix gets verified** (see Bug workflow), and the build must pass before you say you're done.
6. **Don't add warnings.** The release build has 9 known warnings (self-capture in closures). Keep it at 9 or fewer.
7. **Don't hand-edit vendor/.** It's third-party code (uBlock Origin Lite, Kagi bangs); update it by replacing it from upstream.
8. **Don't run ./build.sh in ~/sorrel without asking.** Its first step deletes build/Sorrel.app, the copy the owner runs, which is usually open. In a task worktree it's fine: that's how build/SorrelTest.app gets rebuilt for tests. Use `swift build` to check that things compile.

### Security invariants (re-check whenever you touch related code)
- Private windows always use a non-persistent WKWebsiteDataStore (Web.swift: makeConfiguration, store(for:)), never the default store. Private downloads, history, and session restore leave nothing on disk after the window closes.
- Never auto-grant a permission. Camera/mic in private windows ask every time (Web.swift ~656-668).
- The `sorrel-insecure:` link works only from Sorrel's own warning page. A web page must not be able to link to it to skip the warning.
- ChromeCompat's chrome.runtime page bridge goes only to the sites a Chrome-store extension lists under `externally_connectable` (Extensions.swift: `companionSites`; today just Proton Pass's `account.proton.me` and `pass.proton.me`). Don't widen that, and ask before an extension whose list uses wildcard hosts gets it. In code, `ChromeCompat.exactHostPatterns` leaves wildcard-host patterns out of both the Chrome identity and the bridge (WebKit's own `browser.runtime` for those pages is unaffected).
- openInOtherApp always asks before launching another app. File uploads reach only files the user picked.
- The URL bar always shows the real origin of the page; lookalike international domains display as punycode.
- Content blocking stays on by default. A broken site gets a per-site toggle, never a global off switch.
- The updater installs only updates whose signature verifies. Never weaken that check. SorrelUpdater is deliberately signed without the app's entitlements; keep it that way.

### Commands
- Fast compile check: `swift build` (debug). Release compile: `swift build -c release`.
- Package: `./build.sh` (ask first in ~/sorrel, rule 8). Updater test: `tools/update-test.sh`.
- Only Command Line Tools are installed, not Xcode: don't use xcodebuild.
- Manual tests: run build/SorrelTest.app with the env-var hooks in the Testing section. Use a fresh folder per run (`mktemp -d /private/tmp/sorrel-test.XXXXXX`; the sandboxed test build can only write under /private/tmp) rather than deleting old ones.

### Bug workflow
1. Take the bug from BUGS.md (create it if missing: repro steps, expected, actual).
2. Reproduce it first, using the SorrelTest.app hooks (e.g. SORREL_SNAPSHOT) or a written repro. Say so if you can't.
3. Fix the root cause with the smallest change that works.
4. Verify: the build passes, the repro now behaves correctly, and nearby features still work.
5. Mark it fixed in BUGS.md with a one-line cause, and put anything unfinished in PROGRESS.md.
One bug per session where possible.

### Hooks (.claude/)
- A Stop hook compiles the project when Swift files have changed. If it reports errors, fix them.
- A security hook flags risky patterns in your edits. When it fires, check the change against the invariants above, and list every flagged item in your final summary so I can review it.
